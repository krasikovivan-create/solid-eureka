# Ускоритель GEMM int8: архитектура (шаг 1)

Статус: **выбран вариант V2 (16×16, MT = 128, KMAX = 1024, 304 КиБ SRAM), ПЛИС —
ECP5 LFE5U-85F.** RTL реализован в `rtl/`. Цифры в этом документе — оценки шага 1 по
формулам и по калибровочному синтезу одного PE (см. «Как получены оценки»), а не
измерения готового устройства. Измерения (такты, частота, ресурсы, сравнение с CPU)
собраны в `benchmarks/results.md`.

## 1. Задача и рамки

Вычисление: `C[M×N] (int32) = A[M×K] (int8) · B[K×N] (int8)`, знаковые int8, накопление
в int32 с переполнением по модулю 2³² (как `np.int32`). Результат RTL должен побитово
совпасть с эталоном на NumPy.

Ориентир по архитектуре из задания: общая память с высокой пропускной способностью,
систолический массив 16×16, большой on-chip буфер. Фото Mac mini в задании я понимаю как
пример SoC с общей (unified) памятью: CPU и ускоритель работают с одной DRAM, данные не
копируются между «памятью хоста» и «памятью ускорителя». Характеристики конкретных
коммерческих чипов здесь не используются. Сравнение с ними будет только на шаге 8, в
таблице с источниками.

Что не входит в прототип: свёртки (только GEMM; im2col делает хост), квантизация и
реквантизация выхода (выход — int32), разреженность, несколько ускорителей.

## 2. Блок-схема

```
                     общая память (DRAM, unified), шина BUS байт/такт
                                    ▲        │
                         запись C   │        │ чтение A, B
                                    │        ▼
 ┌──────────────────────────────── mem_if ─────────────────────────────────┐
 │  арбитраж: 1 запрос на чтение/такт, 1 бит записи/такт; ответы по порядку  │
 └───────┬──────────────────────────────────────────────────────▲──────────┘
         │ dma_rd (2D-дескрипторы, маска K-хвоста)               │ dma_wr (строб N-хвоста)
         ▼                                                      │
 ┌───────────────┐   ┌───────────────┐                  ┌───────┴────────┐
 │ A-буфер       │   │ B-буфер       │                  │ ACC-буфер      │
 │ 2 слота       │   │ 2 слота       │                  │ 2 слота        │
 │ MT×KMAX байт  │   │ KMAX×P байт   │                  │ MT×P×int32     │
 │ слово = P байт│   │ слово = P байт│                  │ слово = P×32 бит│
 └──────┬────────┘   └──────┬────────┘                  └───────▲────────┘
        │ строка A[m][k0:k0+P]  │ строка B[k][j0:j0+P]          │ +=
        ▼ (1 слово/такт)        ▼ (P тактов на блок весов)       │
   ┌─────────┐        ┌──────────────────────┐          ┌───────┴───────┐
   │ скос    │───────▶│ систолический массив │─────────▶│ выравнивание  │
   │ (skew)  │  a →   │ P×P PE, weight-      │ psum ↓   │ (deskew) +    │
   └─────────┘        │ stationary, 2 банка  │          │ сложение int32│
                      │ весов в каждом PE    │          └───────────────┘
                      └──────────────────────┘
 ┌─────────────────────────────────────────────────────────────────────────┐
 │ controller: регистры (CSR), три автомата: загрузчик (A/B → буферы),     │
 │ секвенсор вычислений (веса + поток строк A), писатель (ACC → C);        │
 │ счётчики производительности (такты всего / работы / простоя по причинам) │
 └─────────────────────────────────────────────────────────────────────────┘
```

## 3. Поток данных: почему weight-stationary

Рассматривались два варианта систолического массива.

* **Output-stationary** (каждый PE копит один `C[i][j]`). Требует подавать столбцы A, то есть
  транспонировать A при загрузке, и выгружать P² сумм из массива. Без теневых регистров
  массив простаивает во время выгрузки; с ними сложное управление, потому что PE получают
  итоговые суммы в разные такты из-за скоса.
* **Weight-stationary** (как в TPU v1 [1]). PE(i,j) хранит вес `B[k0+i][j0+j]`. Строки A
  проходят слева направо, частичные суммы сверху вниз, накопление по K идёт вне массива, в
  ACC-буфере. Обе матрицы читаются в естественном построчном (row-major) порядке: слово
  A-буфера равно `A[m][k0:k0+P]`, слово B-буфера равно `B[k][j0:j0+P]`. Флаги управления
  идут вместе с данными, поэтому выгрузка из массива не нужна.

Выбран **weight-stationary**.

Временная диаграмма (такты от входа строки m в массив, `t_m`):

* строка i массива получает `A[m][k0+i]` в такт `t_m + i` (скос);
* PE(i,j) — две стадии: `prod ← a·w[bank]` (вес выбирается в такт, когда `a` на входе PE),
  затем `psum_out ← psum_in + prod`; `a_out ← a`, флаг банка идёт вместе с `a`. Регистр
  произведения есть в каждом PE, поэтому сдвиг одинаков для всех и выравнивание волнового
  фронта сохраняется;
* низ столбца j выдаёт `Σ_i A[m][k0+i]·B[k0+i][j0+j]` в такт `t_m + P + 1 + j`. Выравнивание
  задерживает столбец j на `P−1−j`, и строка результата целиком выходит в такт `t_m + 2P`;
* между блочной памятью и массивом стоят регистры: на адресе чтения и на данных. Данные
  A и веса B проходят одинаковое число тактов (3 от выдачи секвенсором до входа массива),
  поэтому правила ниже записаны в тактах выдачи секвенсора и от этих регистров не зависят;
* разрядность частичной суммы в массиве: `16 + log2(P)` бит (для P=16 это 20 бит, точно,
  без переполнения). На выходе она расширяется до int32.

Загрузка весов. В каждом PE два банка весов. Пока блок `b` использует банк `b mod 2`, в
другой банк записывается блок `b+1`: по одной строке весов за такт. Это P байт из
B-буфера по шине столбца, запись в строку i в такт `L+i`. Из условий скоса следуют два
правила:

* загрузку блока `b+1` можно начинать не раньше `t_start(b) + P − 1`: банк должен
  освободиться от блока `b−1` во всех столбцах;
* блок `b+1` можно запускать с `t_start(b+1) ≥ t_start(b) + P`.

Итог: блок из `MT_eff` строк занимает `max(MT_eff, P)` тактов. При `MT_eff ≥ P` массив
работает без пауз на смену весов. Первому блоку достаточно 1 такта после начала загрузки,
потому что скос загрузки совпадает со скосом данных.

## 4. Тайлинг и гнездо циклов

```
for m0 in 0..M step MT:                 # панель A[m0:m0+MT, 0:K] лежит в A-буфере (слот m0/MT mod 2)
  for j0 in 0..N step P:                # панель B[0:K, j0:j0+P] лежит в B-буфере (слот j mod 2)
    for k0 in 0..K step P:              # блок весов P×P → массив
      for m in m0..m0+MT_eff-1:         # 1 строка A за такт
        ACC[m-m0][0:P] (=|+=) psum      # '=' при k0 == 0, '+=' иначе
    ACC-слот → C[m0:m0+MT_eff, j0:j0+P] # dma_wr, параллельно со следующим j0
```

Двойная буферизация (ping-pong) всех трёх буферов позволяет загружать следующую панель A и
следующую панель B и выгружать готовый тайл C одновременно с вычислением. Не перекрываются
только пролог (первая панель A и первая панель B) и эпилог (конвейер массива и последний
тайл C).

Трафик общей памяти (в байтах занятости шины):

* A: `M · ⌈K/P⌉ · P` — каждая строка A читается один раз;
* B: `⌈M/MT⌉ · ⌈N/P⌉ · K · P` — вся B перечитывается для каждой панели A. **Чем больше
  A-буфер (MT), тем меньше трафик B** — в этом смысл большого on-chip буфера;
* C: `M · ⌈N/P⌉ · 4P` — int32 пишется один раз.

Отношение MAC к байтам трафика ≈ `1 / (1/N + 1/MT + 4/K)`. Чтобы массив не ждал память,
нужно примерно `P² · (1/N + 1/MT + 4/K)` байт/такт.

Завершение задания: `done` выставляется, когда секвенсор прошёл все блоки, оба ACC-слота
выгружены и **общая память приняла последний бит записи**. Регистровый слайс в `mem_if`
должен быть пуст. Первая версия RTL ждала только выгрузки из ACC. При полосе ≤ 2 байт/такт
это теряло последний бит C. Ошибку нашла развёртка по полосе памяти, сейчас её
покрывают тесты.

Ограничения прототипа (проверяются контроллером, иначе бит ошибки в STATUS):
`K ≤ KMAX`; адреса и шаги строк (lda, ldb, ldc) кратны BUS байтам; M, N, K любые ≥ 1.
Хвосты обрабатываются аппаратно: байты A с `k ≥ K` зануляются при загрузке, столбцы C с
`j ≥ N` не пишутся (строб), строки `m ≥ M` не подаются в массив.

## 5. Интерфейс памяти и модель общей памяти

Шина шириной `BUS = P` байт. Одно слово буфера передаётся за один такт.

* Чтение: запрос `(addr, len ≤ 256 бит)` с `valid/ready`. Ответы приходят по порядку, по
  одному биту за такт, без back-pressure: загрузчик выдаёт запрос, только когда в слоте
  есть место.
* Запись: побитово, `(addr, data, strb)` с `valid/ready`.
* Модель памяти (`tb/mem_model.sv`, только для симуляции): фиксированная задержка чтения
  `LAT` тактов и общий для чтения и записи лимит пропускной способности: не больше
  `BW_NUM/BW_DEN` бит за такт, по умолчанию 1 бит, то есть BUS байт/такт. Задержку и
  пропускную способность можно менять, чтобы показать зависимость от памяти.

«Высокая пропускная способность» здесь означает **байт/такт относительно вычислительной
мощности**: шина P байт/такт при пике P² MAC/такт. Абсолютные ГБ/с зависят от частоты,
а частоту укажу только после синтеза.

## 6. Узкие места (в порядке значимости)

1. **Пропускная способность общей памяти.** Нужно `P²·(1/N + 1/MT + 4/K)` байт/такт.
   Пик массива растёт как P², а шина в этой архитектуре как P. Поэтому большой массив
   упирается в память раньше маленького. Для 32×32 на задачах 128³ и с малым K память
   ограничивает загрузку примерно до 50% (см. таблицу ниже).
2. **Выход int32.** При малом K основной трафик — запись C: `4/K` в формуле. Пример:
   1024×1024×64 на 16×16 требует ≈18 байт/такт при шине 16, то есть упирается в память.
   Реквантизация выхода в int8 снизила бы это слагаемое в 4 раза, но в прототип она не
   входит.
3. **Малое M (батч 1, GEMV).** Каждый вес используется один раз. Загрузка блока весов
   (P тактов) не окупается, загрузка массива ≈ `M/P` (6% для 16×16), а трафик весов
   `K·N` байт ограничивает скорость примерно 1 MAC на байт памяти. Это фундаментальное
   свойство GEMV, а не недостаток реализации. Отмечу его в результатах.
4. **Пролог и эпилог.** Первую панель A (`MT·K/P` тактов) и первую панель B (`K` тактов)
   нельзя перекрыть вычислением. На маленьких задачах (128³) это заметная доля времени.
5. **Порты буферов.** На такт нужно 1 слово A, 1 слово B (при загрузке весов) и
   чтение-изменение-запись `P×32` бит в ACC. Каждому потоку выделен свой буфер с отдельными
   портами чтения и записи, поэтому конфликтов нет. Это стоит площади: ACC-слово для 16×16
   имеет ширину 512 бит.
6. **KMAX.** Панель A хранит всю длину K. Для `K > KMAX` нужно разбиение по K с
   промежуточными суммами в памяти. В прототип это не входит.

## 7. Варианты конфигурации

Во всех вариантах шина равна P байт/такт, буферы ping-pong. Размеры буферов:
`A = 2·MT·KMAX`, `B = 2·KMAX·P`, `ACC = 2·MT·P·4` байт.

| | V1 «компактный» | **V2 «опорный»** | V3 «крупный» |
|---|---|---|---|
| Массив | 8×8 | **16×16** | 32×32 |
| Пик, MAC/такт | 64 | **256** | 1024 |
| MT (строк A в панели) / KMAX | 64 / 1024 | **128 / 1024** | 256 / 2048 |
| A / B / ACC буферы, КиБ | 128 / 16 / 4 | **256 / 32 / 16** | 1024 / 128 / 64 |
| On-chip SRAM всего | 148 КиБ | **304 КиБ** | 1216 КиБ |
| Шина памяти, байт/такт | 8 | **16** | 32 |
| Умножителей 8×8 | 64 | **256** | 1024 |
| Триггеров в массиве (оценка) | ≈2,9 тыс. | **≈11,8 тыс.** | ≈48 тыс. |
| ECP5 LFE5U-85F: DSP (из 156) | 64 | **156 + 100 PE с умножителем на LUT** | не помещается |
| ECP5: LUT4 (из 83 640), оценка | ≈8–11 тыс. | **≈56–75 тыс. (67–90%)** | не помещается |
| ECP5: EBR (из 208), оценка | ≈90 | **≈175** | не помещается (нужно ≈600+) |

Как получены оценки площади:

* Триггеры массива: `P²·(8 + 2·8 + (16+log2 P) + 2)` бит на PE: a, два веса, частичная
  сумма, флаги.
* LUT/DSP: калибровочный синтез прототипа PE в Yosys 0.33 (`synth_ecp5`) и размещение в
  nextpnr-ecp5 0.6 (`--85k --out-of-context`).
  * С умножителем в DSP: 1 MULT18X18D, 46 LUT4, 46 DFF на PE.
  * С умножителем на LUT (`-nodsp`): 440–600 LUT4 на PE. Разброс зависит от того, как
    записан умножитель; Yosys 0.33 не умеет Booth-кодирование.
  * К этому добавлена инфраструктура (DMA, контроллер, сложение в ACC): 5–8 тыс. LUT4.
    Это грубая оценка.
* Ёмкость ECP5-85F (83 640 LUT4, 156 MULT18X18D, 208 DP16KD) — из отчёта nextpnr-ecp5.
* EBR: блок 18 Кбит используется как 2048×8 бит (без чётности), то есть 2 КиБ данных. Для
  ACC-слова 512 бит выбирается конфигурация 512×36.
* Площадь в мм² для ASIC **не оцениваю**. Для этого нужна библиотека стандартных ячеек и
  SRAM-макросы, а подставлять чужие цифры без проверки правила проекта запрещают. Из
  таблицы видно, что в V2 и V3 по площади, скорее всего, преобладает SRAM: 304 КиБ ≈
  2,5 Мбит против ≈12 тыс. триггеров массива.

проверено уменьшением `BW_NUM/BW_DEN`.

### Рекомендация

**V2 (16×16, 304 КиБ)**:

* совпадает с ориентиром из задания;
* на больших задачах оценка загрузки 96–99% при запасе по полосе в 2–5 раз;
* по оценке помещается в ECP5 LFE5U-85F, правда с запасом всего 10–33% по LUT, так что
  частота после размещения может оказаться невысокой.

V1 надёжно помещается в ПЛИС, но даёт в 4 раза меньший пик. V3 не помещается ни в одну
ПЛИС с открытым маршрутом (Yosys + nextpnr), и на задачах ≤ 256³ его ограничивает память.

RTL параметризуется (`P`, `MT`, `KMAX`), поэтому V1 и V3 можно будет прогнать в симуляции
как дополнительные точки. Синтез на ПЛИС — только для выбранного варианта.

## 8. Методика проверки и замеров (шаги 3–7)

* Эталон: `C = (A.astype(int64) @ B.astype(int64))`, затем приведение к int32 с
  переполнением. Для `K ≤ 1024` переполнения нет: `|C| ≤ 1024·2¹⁴ = 2²⁴`.
* pytest: случайные и краевые матрицы (−128 и 127, нули), размеры, не кратные P,
  «мусор» в паддинге строк. RTL сравнивается с эталоном побитово в Verilator и Icarus
  Verilog.
* Счётчики в RTL: всего тактов (от `start` до `done`), тактов работы массива (в массив
  входит строка A), тактов простоя по причинам: ожидание данных A/B, ожидание
  ACC-слота/записи, смена весов. Простой ядра = 1 − работа/всего. Эффективная загрузка
  = `M·N·K / (P²·такты)`.
* Производительность: `2·M·N·K · f / такты` операций/с, где `f` — частота после
  размещения и трассировки (nextpnr), а не желаемая.
* CPU-база: NumPy на машине, где идёт сборка. Здесь это контейнер с Intel Xeon @ 2,80 ГГц,
  4 vCPU под KVM, не Mac mini. Несколько прогонов, медиана, версии библиотек.
  Целочисленный `np.matmul` не использует BLAS. Поэтому отдельно замеряю float32/float64
  через BLAS: результат точен при `|C| < 2²⁴` и `< 2⁵³` соответственно. Ускорение покажу
  относительно обоих вариантов, чтобы не выбирать удобную базу.
