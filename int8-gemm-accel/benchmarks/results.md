# Результаты: ускоритель GEMM int8 (16×16) против NumPy на CPU

Все числа ниже, кроме таблицы в разделе 7, — измерения этого проекта. Как их
воспроизвести, описано в `README.md`. Сырые данные лежат в `benchmarks/data/*.json`,
сводные таблицы генерирует `benchmarks/make_report.py` в `benchmarks/results_tables.md`.

## Итог

* **Корректность.** Результат RTL побитово совпадает с эталоном NumPy: 97 тестов pytest,
  полный перебор PE, Verilator и Icarus. Мутационная проверка подтверждает, что тесты
  ловят внесённые ошибки.
* **Такты (симуляция).** На задачах от 256³ массив 16×16 занят 96–99% времени (≈ 245–254 MAC/такт из 256).
  * Малые задачи (64³: 57%) упираются в пролог.
  * Малое K упирается в запись int32-результата (87%).
  * GEMV (батч 1) упирается в загрузку весов (6%). Это свойство weight-stationary, а не ошибка.
* **Частота.** После размещения и трассировки на Lattice ECP5 LFE5U-85F (скорость 6;
  Yosys 0.33 + nextpnr-ecp5 0.6) — **54,0 МГц**. Цель 100 МГц не достигнута. Пик массива
  при этой частоте — 27,6 GOPS, на 512³ получается 27,4 GOPS.
* **Итоговое соотношение с CPU** (Intel Xeon @ 2,8 ГГц, 4 vCPU, NumPy 2.5.3 / OpenBLAS 0.3.34):
  * против заданной базы — целочисленного `numpy.matmul`, int8 → int32 — ускоритель
    **быстрее в 4,3–53 раза** (22× на 512³);
  * против NumPy через OpenBLAS float32 (тот же побитовый результат) ускоритель
    **медленнее в 1,8–6 раз**;
  * против чистого ядра sgemm без преобразований типов — **медленнее в 3,6–17 раз**.
  * **Ускорения относительно сильной CPU-базы нет.** Причина — тактовая частота: 54 МГц
    на ПЛИС против 2,8 ГГц и AVX-512 на 4 ядрах. Архитектурная эффективность (99% загрузки
    массива) при этом высокая. Подробности в разделе 6.


## 1. Конфигурация

| Параметр | Значение |
|---|---|
| Массив | 16×16 PE, weight-stationary, int8 × int8 → int32; в каждом PE регистр произведения и регистр частичной суммы |
| Пик | 256 MAC/такт = 512 оп./такт |
| On-chip SRAM | 304 КиБ: A-буфер 2×128 КиБ (MT = 128 строк × KMAX = 1024), B-буфер 2×16 КиБ, ACC 2×8 КиБ |
| Общая память | одна шина 16 байт/такт, общая для чтения и записи; в симуляции поведенческая модель `tb/mem_model.sv`: задержка 32 такта, ≤ 1 слово шины (16 байт) за такт |
| Ограничения | K ≤ 1024; адреса и шаги строк кратны 16 байтам; выход int32 |
| Синтезируемый вариант | `N_DSP = 64`: умножители 64 PE в DSP MULT18X18D, у остальных 192 PE умножитель на LUT. Выбран по результатам трассировки (раздел 4) |
| RTL | версия 4, коммит `54f500e`: синтезирован он; такты и тесты сняты на том же RTL |

## 2. Проверка корректности

* **97 тестов pytest**, все проходят. Состав:
  * полный перебор всех 65 536 пар (a, w) для обоих вариантов умножителя PE и обоих банков весов (Icarus и Verilator);
  * RTL против эталона NumPy на синтезируемой конфигурации 16×16 (64 PE с DSP + 192 с LUT; отдельно 0/156/256) и на двух малых (4×4, 8×8). Проверяются:
    * хвосты по M, N, K;
    * K = KMAX;
    * несколько панелей A;
    * шаги строк больше минимальных;
    * задержка памяти 1–200 тактов, полоса от 1/13 до 1 слова шины за такт;
    * крайние значения (−128, 127), нули, единичная матрица;
    * ошибки конфигурации;
    * 5 разных заданий подряд без сброса (в буферах остаются данные предыдущих);
    * случайный перебор 60 форм.
* Сравнение **побитовое**: `np.array_equal` с эталоном `(A.astype(int64) @ B.astype(int64))` по модулю 2³². Дополнительно проверяется, что байты паддинга строк C не тронуты: это проверка стробов записи.
* На каждом прогоне проверяются инварианты счётчиков: `такты = работа + простои + хвост`; число тактов работы, прочитанных и записанных слов шины равно расчётному.
* Icarus Verilog 12 и Verilator 5.020 дают одинаковый результат и одинаковые счётчики тактов.
* **Мутационная проверка** (`sim/mutation_check.py`): в RTL по одной вносятся известные ошибки, тесты должны упасть.

  | Внесённая ошибка | Тесты |
  |---|---|
  | знак старшего частичного произведения в LUT-умножителе | ловят |
  | маска K-хвоста A сдвинута на 1 байт | ловят (тест с заданиями подряд) |
  | строб записи игнорирует хвост по N | ловят |
  | аккумулятор игнорирует флаг первого k-блока | ловят |
  | задержка токена в массиве +1 такт | ловят |
  | `done` до приёма памятью последней записи | ловят |
  | загрузка весов на 2 такта раньше (P−3) | ловят |
  | загрузка весов на 1 такт раньше (P−2) | не ловят — **так и должно быть**: по выводу в `docs/architecture.md`, разд. 3, в правиле запас ровно 1 такт |

* **Ошибки, найденные по ходу работы:**
  1. `done` выставлялся до того, как память приняла последнее слово записи. При полосе ≤ 2 байт/такт терялись 4 последних значения C. Ошибку нашла развёртка по полосе памяти (шаг 4). Исправлено, покрыто тестами.
  2. Дыра в тестах: маска K-хвоста не проверялась, потому что в одном задании «лишние» строки B в буфере всегда нулевые. Добавлен тест на несколько заданий подряд.

## 3. Такты в симуляции

Verilator 5.020; память: 16 байт/такт, задержка 32 такта; каждый прогон побитово сверен с эталоном.

| 128^3 | 9,937 | 211.0 | 82.4% | 17.6% | 12.0% / 0.0% / 0.0% / 5.6% | 184.0 µs | 22.79 |
| 256^3 | 68,433 | 245.2 | 95.8% | 4.2% | 3.4% / 0.0% / 0.0% / 0.8% | 1.267 ms | 26.48 |
| 512^3 | 529,489 | 253.5 | 99.0% | 1.0% | 0.9% / 0.0% / 0.0% / 0.1% | 9.805 ms | 27.38 |
| MLP 256x1024x1024 | 1,058,385 | 253.6 | 99.1% | 0.9% | 0.9% / 0.0% / 0.0% / 0.1% | 19.600 ms | 27.39 |
| малое K 1024x1024x64 | 301,020 | 222.9 | 87.1% | 12.9% | 0.2% / 12.5% / 0.0% / 0.2% | 5.574 ms | 24.08 |
| GEMV 1x1024x1024 | 67,965 | 15.4 | 6.0% | 94.0% | 3.5% / 0.0% / 90.4% / 0.1% | 1.259 ms | 1.67 |

* «Загрузка» = `M·N·K / (256 · такты)`, то есть доля пика, включая паддинг по P.
* «Простой ядра» = доля тактов, когда в массив не входит строка A.
* Аналитическая модель шага 1 (`model/perf_model.py`) совпадает с измерением с точностью
  ≤ 0,3% для всех задач ≥ 128³, кроме GEMV (1,4%). Для 64³ модель завышает такты на 22%:
  она пессимистично считает пролог.

Что видно из таблицы:

* **Большие задачи (≥ 256³, MLP).** Загрузка 96–99%. Почти весь простой — пролог: первая
  панель A и первая панель B грузятся до начала вычислений.
* **Малое K (1024×1024×64).** 12,5% тактов массив ждёт выгрузки ACC: трафик записи C в int32
  (4 МиБ) больше, чем успевает уйти за время вычисления. Это узкое место «выход int32»,
  предсказанное в архитектуре.
* **GEMV (батч 1).** Загрузка 6%: каждый блок весов 16×16 грузится 16 тактов и используется
  1 такт. Это фундаментальное ограничение weight-stationary при M < 16, а не ошибка.
* **64³.** Загрузка 57%: пролог и хвост сравнимы со временем вычисления (1 024 такта).

### Размер on-chip буфера

| MT | SRAM всего, КиБ | Полоса, Б/такт | Трафик памяти, КиБ | Такты | Загрузка |
|---:|---:|---:|---:|---:|---:|
| 16 | 66 | 16 | 17,664 | 1,133,153 | 92.5% |
| 16 | 66 | 4 | 17,664 | 4,523,083 | 23.2% |
| 32 | 100 | 16 | 9,472 | 1,054,580 | 99.4% |
| 32 | 100 | 4 | 9,472 | 2,426,955 | 43.2% |
| 64 | 168 | 16 | 5,376 | 1,054,033 | 99.5% |
| 64 | 168 | 4 | 5,376 | 1,379,403 | 76.0% |
| 128 | 304 | 16 | 3,328 | 1,058,385 | 99.1% |
| 128 | 304 | 4 | 3,328 | 1,118,093 | 93.8% |

Здесь виден смысл «большого on-chip буфера». При своей полной шине (16 байт/такт) хватает
MT = 32 (100 КиБ). Но когда ускорителю достаётся 4 байт/такт общей памяти (остальное
занято CPU и т. п.), загрузка растёт так: MT = 16 → 23%, MT = 32 → 43%, MT = 64 → 76%,
MT = 128 → 94%. Буфер 304 КиБ снижает трафик в 5,3 раза относительно 66 КиБ.

## 4. Частота и ресурсы: ПЛИС Lattice ECP5 LFE5U-85F

Инструменты: Yosys 0.33 (git sha1 2584903a060); nextpnr-ecp5 0.6 (пакет Ubuntu 0.6-3build5). Корпус CABGA381, скорость
6 (самая медленная), режим `--out-of-context`: ускоритель размещён как блок SoC, порты не
выведены на ножки. Router2, seed 1. Скрипт: `synth/run_ecp5.sh`. Отчёты лежат в
`synth/reports/`.

**Итог (версия 4, `N_DSP = 64`): Fmax = 54,00 МГц после трассировки.**
Цель 100 МГц не достигнута: nextpnr отмечает это как `FAIL`, но трассировка завершена
полностью. Ниже все частоты — только из отчётов nextpnr.

| Ресурс | Занято | Всего | % |
|---|---:|---:|---:|
| LUT4 (логика + перенос) | 51,383 | 83,640 | 61% |
| Триггеры | 25,059 | 83,640 | 30% |
| Блочная память DP16KD (18 Кбит) | 174 | 208 | 84% |
| DSP MULT18X18D | 64 | 156 | 41% |

Оценка шага 1 — «≈175 EBR, 56–75 тыс. LUT4» для 156 DSP — по памяти совпала (174 EBR).
По логике прямое сравнение невозможно: финальный вариант использует 64 DSP вместо 156.

### Как получена частота: итерации

| RTL | N_DSP | Роутер | Оценка после размещения, МГц | После трассировки | Что изменено / критический путь |
|---|---:|---|---:|---|---|
| v1 (`3be77ca`) | 156 | router1 | 25,76 | не оттрассирован | исходный RTL; трассировка router1 остановлена через ~45 мин (не сходилась) |
| v2 (`d1469ae`) | 156 | router2 | 30,41 | не оттрассирован | регистр после чтения буферов, регистр произведения в PE, 3-стадийный ACC; router2 не сошёлся (перегрузка росла), остановлен |
| v3 (`feef8eb`) | 64 | router2 | 40,95 | 41,72 МГц | + регистр адреса чтения буферов; крит. путь: адрес A-буфера -> ~120 EBR (23,2 нс разводки) |
| v3 (`feef8eb`) | 0 | router2 | 36,00 | 46,97 МГц | то же, без DSP; крит. путь: логика ответа dma_rd (18,6 нс разводки) |
| v4 (`54f500e`) | 64 | router2 | 44,75 | 54,00 МГц | буферы по байтовым дорожкам с копиями адреса, dma_rd на счётчиках; крит. путь 18,5 нс (81% разводка): флаг банка весов PE(10,10) -> соседний PE через пол-кристалла (8,7 нс) + LUT-умножитель |
| v4 (`54f500e`) | 0 | router2 | 39,79 | 53,79 МГц | то же, без DSP; крит. путь: write-DMA -> разрешение чтения ACC (16,9 нс разводки) |

Что показали итерации:
1. **Связность решётки против геометрии DSP.** Решётка 16×16 PE связана с соседями по
   горизонтали и вертикали. У ECP5 все 156 DSP стоят в фиксированных рядах. Когда заняты
   все DSP, соседние PE разносятся далеко, вокруг рядов DSP возникает перегрузка, и
   router2 не сходится. С 64 DSP или без DSP дизайн трассируется.
2. **Разветвление на блочную память.** Один регистр адреса на ~120 блоков EBR давал 23 нс
   одной только разводки. Исправлено разбиением буфера на 16 байтовых дорожек со своими
   копиями регистров.
3. Оставшиеся пути (≈18 нс) — тоже в основном разводка, 81–91% задержки: длинные трассы
   внутри массива (массив растянут между рядами DSP и блочной памятью), write-DMA →
   разрешение чтения ACC. Следующий шаг —
   регистры на этих трассах. Он не сделан: по оценке это +5–10% за итерацию длиной ~40 мин.

Отдельный PE (вход и выход через регистры) размещается на 121,7 МГц с DSP и на 111,2 МГц
с LUT-умножителем. Потолок задаёт не арифметика, а разводка большого массива и буферов на
кристалле. Разброс по seed не исследовался: запускался только seed 1.


## 5. Базовая реализация на CPU

Скрипт: `benchmarks/cpu_baseline.py`, данные: `benchmarks/data/cpu_baseline.json`.

* **CPU:** Intel(R) Xeon(R) Processor @ 2.80GHz, 4 vCPU (4 ядра, 1 поток
  на ядро), виртуальная машина KVM, AVX-512 (включая VNNI). L2 4 МиБ,
  L3 33 МиБ.
* **ПО:** Python 3.13.16, NumPy 2.5.3, BLAS — scipy-openblas 0.3.34.106.0 (OpenBLAS, ядро
  SkylakeX, 4 потока).
* **Методика:** 2 прогона прогрева, затем не меньше 7 прогонов и не меньше ~1 с на
  вариант (до 51 прогона). В таблице — медиана. Все варианты дают результат, побитово
  равный эталону: проверено перед замером. Машина во время замера была свободна:
  синтез не шёл.
* **Варианты:**
  * `numpy_int32` — `A.astype(int32) @ B.astype(int32)`, **база из задания**;
    целочисленный matmul в NumPy не использует BLAS;
  * `numpy_f32_blas` / `numpy_f64_blas` — через sgemm/dgemm OpenBLAS и обратно в int32;
  * `numpy_f32_blas_1thread` — то же, OpenBLAS в 1 потоке;
  * `f32_kernel_only` — только sgemm на заранее преобразованных входах: самый выгодный
    для CPU вариант.

| MLP 256x1024x1024 | 53.18× | 0.41× | 0.20× | 0.34× | 0.14× |
| малое K 1024x1024x64 | 13.53× | 0.53× | 0.33× | 0.49× | 0.10× |
| GEMV 1x1024x1024 | 4.28× | 0.25× | 0.56× | 1.02× | 0.06× |

**Вывод: относительно сильной CPU-базы ускорения нет.** Прототип на ПЛИС в 1,8–6 раз
медленнее NumPy+OpenBLAS (float32, 4 потока) и в 3,6–17 раз медленнее чистого sgemm.
Быстрее он только базовой целочисленной реализации NumPy (в 4,3–53 раза), но она сама по
себе медленная: NumPy не использует BLAS для целых типов.

Почему так:

1. **Частота.** Ускоритель делает 512 оп./такт, но на 54 МГц это всего 27,6 GOPS пика.
   Четыре ядра AVX-512 на 2,8 ГГц через OpenBLAS дают в этой VM 137–237 GOPS на больших
   задачах (измерено). Чтобы те же такты сравнялись по времени со `numpy_f32_blas`, нужна
   частота около 270–320 МГц на 512³ и MLP; с чистым sgemm — около 400–450 МГц. Это
   арифметика на измеренных числах, а не обещание: такую частоту на ECP5 этот RTL не
   показал.
2. **Архитектура тут не узкое место.** На больших задачах массив занят 99% тактов,
   трафик памяти совпадает с расчётом, полосы 16 байт/такт хватает с запасом в 3–5 раз.
   Значит, при той же логике производительность растёт пропорционально частоте и числу
   MAC. Но это вывод о масштабировании, а не измерение.
3. **Слабые места самой архитектуры** (раздел 3):
   * GEMV и батч 1 — 6% загрузки, потому что веса используются однократно;
   * малое K — запись результата int32;
   * малые задачи — пролог.
   На GEMV ускоритель лишь сравнялся с `numpy_f64_blas` (1,02×) и медленнее остальных
   вариантов BLAS.
4. Энергию и стоимость не сравнивал: мощность ПЛИС и CPU не измерялась.

## 8. Ограничения и оговорки

* **Память — модель.** `tb/mem_model.sv` — поведенческая модель: фиксированная задержка
  и лимит слов шины за такт. Банков DRAM, страниц, регенерации и конкуренции с CPU в ней нет.
  Реальная общая память даст другие задержки. Развёртка в разделе 3 показывает, насколько
  результат от этого зависит.
* **Время ускорителя — расчётное:** такты из RTL-симуляции, делённые на частоту из
  nextpnr. На плате ничего не запускалось: платы нет. Время CPU — прямой замер.
* **CPU-замер сделан не на Mac mini.** Это облачная VM: Intel Xeon @ 2,80 ГГц, 4 vCPU,
  KVM. Скрипт `benchmarks/cpu_baseline.py` переносим, на другой машине результат будет
  другим.
* **Что входит во время ускорителя:** от `start` до `done`, включая чтение A и B из общей
  памяти и запись C. Копирования между памятью хоста и ускорителя нет: память общая.
  Программирование регистров (~10 записей) не входит.
* **CPU-база** считает ту же задачу: вход int8, выход int32, побитово тот же результат.
  Целочисленный `matmul` в NumPy не использует BLAS. Поэтому приведены и float32/float64
  через OpenBLAS: они точны для K ≤ 1024, это проверено. Оптимизированные int8-библиотеки
  для CPU (oneDNN, VNNI) не измерялись: CPU ими, вероятно, был бы ещё быстрее.
* **Энергия и мощность не измерялись**, поэтому выводов о производительности на ватт нет.
* **Прототип:** K ≤ 1024, выравнивание на 16 байт, выход только int32, без реквантизации
  и свёрток.
