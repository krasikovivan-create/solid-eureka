# Принятые решения

Задание было выполнить всё за одну сессию без уточняющих вопросов. Здесь записано, что
я решил сам и почему.

## Размещение и деплой

1. **Папка `ai-employee/` в репозитории `solid-eureka`.** В репозитории уже лежат другие
   проекты (`shop-bot/`, `telegram-bot/`, …), поэтому бот живёт в своей папке и не мешает
   им. На Railway это Root Directory `ai-employee`.
2. **Сборка через Dockerfile, а не Nixpacks/Railpack.** Сборка предсказуемая и
   одинаковая везде. `railway.json` задаёт сборку, команду `python -m app`,
   health-check `/health` и перезапуск при сбое. Railway не подхватывает
   `railway.json` из Root Directory сам, поэтому в SETUP.md путь указан абсолютный:
   `/ai-employee/railway.json`. Через `watchPatterns` бот пересобирается только при
   изменениях в своей папке.
3. **Long polling вместо webhook.** Публичный домен и секрет для webhook не нужны —
   меньше шагов с телефона. Одного экземпляра для команды из нескольких человек хватает.
4. **Health-check на aiohttp-сервере, который работает рядом с polling.** На порту `$PORT`
   `/health` проверяет доступ к БД. Railway смотрит на него при деплое.
5. **Контейнер работает от root, в Dockerfile нет `VOLUME`.** Volume на Railway
   монтируется с правами root (у пользователя без root нет прав на запись), а
   инструкцию `VOLUME` Railway не принимает. `DB_PATH=/data/bot.db` задан по умолчанию
   в Dockerfile, но в SETUP его всё равно просим указать явно.
6. **Запуск без падений из-за сети.** При старте бот проверяет токен. Если токен
   неверный, в логе понятное сообщение и выход с кодом 1. Сетевые сбои повторяются с
   паузой. Если не заданы обязательные переменные, бот сразу их перечисляет.

## Данные

7. **SQLite + SQLAlchemy async (aiosqlite), схема через `create_all`.** Для одного
   экземпляра и одной компании этого достаточно. Alembic не нужен, пока нет данных для
   миграции: новые таблицы создаются сами. WAL и `busy_timeout` включены, чтобы
   одновременные запросы не мешали друг другу.
8. **Время в БД хранится в UTC** (`UTCDateTime`), а показывается и вводится в часовом
   поясе компании (по умолчанию Europe/Moscow, меняется в `/settings`).
9. **Одна компания на экземпляр бота.** Профиль компании, клиенты, база знаний и факты
   общие для всех разрешённых пользователей. Задачи, история диалога и аудиты у
   каждого свои. Утренние и вечерние сводки получают все разрешённые пользователи,
   которые хоть раз нажимали `/start`.
10. **Файлы (документы, КП) лежат рядом с базой** в `/data/documents` и
    `/data/proposals`, то есть на том же Volume.

## Агент и ИИ

11. **Собственный цикл tool use поверх `AsyncAnthropic.messages.create`** вместо beta
    Tool Runner. Так проще считать расходы по каждому запросу, ограничивать число шагов
    (`MAX_TOOL_ITERATIONS`) и складывать побочные результаты инструментов (файлы,
    кнопки подтверждения, начало аудита) в `outbox`. Обработчик Telegram отправляет их
    после ответа.
12. **Выбор модели.** Обычный диалог идёт через `MODEL_FAST` (Haiku 4.5): он дешёвый и
    быстрый. Длинные сообщения (>600 символов) и аналитические просьбы («проанализируй»,
    «предложи стратегию»…) идут через `MODEL_SMART`. Отчёт аудита, КП и тексты всегда
    пишет `MODEL_SMART` (Sonnet 5.5).
13. **Effort.** Для диалога на Sonnet `low`, для текстов `low`, для аудита и КП `medium`.
    Haiku 4.5 параметр effort не поддерживает, поэтому для него он не передаётся.
14. **Структурированный вывод** (`output_config.format` с JSON Schema) для отчёта аудита
    и КП. Есть запасной разбор JSON из текста, а итоги (суммы часов, стоимость) считает
    код, а не модель.
15. **Стоимость в КП = трудоёмкость этапа (часы от модели) × ставка компании**
    (`/settings`, по умолчанию 3000 ₽/ч). Цены получаются предсказуемыми и
    управляемыми, а модель не придумывает рубли.
16. **Отказы модели (`stop_reason: refusal`).** Если отказался `MODEL_SMART`, запрос
    повторяется на `MODEL_FAST`, иначе пользователь получает вежливое сообщение.
    Серверный beta-параметр `fallbacks` я сознательно не включал: его нельзя проверить
    без сети, а ошибка в нём сломала бы все запросы. Клиентский откат решает ту же
    задачу.
17. **Кэширование промпта.** Системный промпт разделён на статичную часть с
    `cache_control` (вместе с описаниями инструментов) и динамическую (профиль, текущее
    время, факты, резюме). Повторные запросы так дешевле.
18. **Даты разбирает модель, а не регулярные выражения.** В промпте указаны текущие дата,
    время и часовой пояс. Модель переводит «завтра в 10» в `2026-10-03T10:00`, а код
    строго проверяет формат и переводит в UTC. Если указан срок со временем, а время
    напоминания нет, напоминание ставится на срок.
19. **Удаление никогда не выполняется инструментом напрямую.** Инструмент только
    показывает кнопку «Да, удалить / Отмена», удаляет обработчик кнопки. Это относится
    и к фразам («удали клиента»), и к кнопкам меню.
20. **Тексты (`write_text`) отправляются пользователю сразу из инструмента**, а агент
    только коротко комментирует. Так модель не пересказывает текст ещё раз и не тратит
    токены впустую.
21. **Память.** В запрос дословно передаются последние `HISTORY_LIMIT` (20) сообщений.
    Когда накапливается ещё 10 сверх лимита, более старые сжимаются быстрой моделью в
    резюме (в фоне после ответа). Факты сохраняются инструментом `remember_fact`, и 60
    последних всегда есть в системном промпте. `/new` очищает историю, но не факты.

## Функции

22. **Напоминания — это поле `remind_at` у задачи.** Отдельной таблицы нет:
    «напомни позвонить» — это задача, а follow-up — задача, привязанная к клиенту.
    APScheduler держит задания в памяти, но при старте они восстанавливаются из БД.
    Пропущенные за время простоя отправляются сразу. Раз в минуту страховочная проверка
    отправляет напоминания, у которых почему-то нет задания.
23. **Утренняя и вечерняя сводки собираются без ИИ**, по данным из БД. Это бесплатно,
    мгновенно и не зависит от доступности API.
24. **Онбординг хранит текущий шаг в БД** (`onboarding_step`), поэтому переживает
    перезапуск. Остальные короткие состояния ввода (поле в `/settings`, имя клиента для
    аудита) лежат в MemoryStorage aiogram: их потеря не критична.
25. **Аудит — фиксированные 10 вопросов**, ответы и шаг лежат в таблице `audits`. Так
    интервью предсказуемо, его можно прервать и продолжить после перезапуска, а
    стоимость не зависит от числа уточнений. Любой вопрос можно пропустить. Пока аудит
    идёт, все текстовые сообщения считаются ответами, `/cancel` прерывает его.
26. **BM25 написан вручную** (около 100 строк) с простым стеммером для русского
    (отсечение окончаний) и стоп-словами. Без зависимостей и внешних сервисов
    эмбеддингов. Документы режутся на фрагменты по ~1200 символов с перекрытием.
    Индекс строится лениво и сбрасывается при добавлении или удалении документа.
27. **Форматы базы знаний: PDF (pypdf), DOCX (python-docx, включая таблицы), TXT**, а
    также MD и CSV. Для TXT кодировка определяется перебором: UTF-8 → CP1251 → KOI8-R.
    Сканы PDF без текстового слоя бот вежливо отклоняет: OCR в задачу не входил.
28. **Голосовые и фото пока не обрабатываются.** Бот вежливо просит написать текстом.
    Это вне списка функций.

## Расходы и ошибки

29. **Цены моделей лежат в `config.py`** (Sonnet 5.5 — $2/$10, Haiku 4.5 — $1/$5 за 1M
    токенов, кэш: запись ×1.25, чтение ×0.1). Каждый запрос записывается в
    `usage_records`. Бюджеты `DAILY_BUDGET_USD` / `MONTHLY_BUDGET_USD` проверяются до
    запроса.
30. **Ошибки.** Ошибки API превращаются в понятные сообщения (ключ, баланс, перегрузка,
    лимит запросов). Ошибки инструментов возвращаются модели как `is_error`, и она
    объясняет их человеку. Всё непредвиденное ловит глобальный обработчик aiogram: пишет
    стек в лог и отвечает «Что-то пошло не так…». Молча бот не падает.
31. **Разметка Telegram — HTML.** Markdown из ответов модели безопасно конвертируется
    (всё экранируется). Если Telegram всё же отклонит разметку, сообщение уходит простым
    текстом. Длинные ответы режутся на части.

## Тесты

32. **Сеть в тестах не используется.** Anthropic заменён `FakeAnthropic` (ответы по
    сценарию), Telegram — `MockedSession` aiogram (запоминает запросы, отдаёт файлы для
    скачивания). Сквозные тесты гоняют настоящие апдейты через диспетчер: онбординг,
    доступ, диалог с инструментами, удаление с подтверждением, загрузку документа и
    вопрос по нему, полный аудит с КП в DOCX. Отдельный тест запускает приложение
    целиком (health-check, планировщик, polling) и корректно его останавливает.
33. **CI в GitHub Actions** (`.github/workflows/ai-employee.yml`) запускает ruff, тесты и
    сборку Docker-образа для изменений в `ai-employee/`.
